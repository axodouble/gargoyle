# Role Invite Trees Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Guild roles can be opted into a Lobste.rs-style invite tree: holders invite other members via `/role invite invite <user> [role]`, the invite is an accept/deny offer (chat buttons + DM jump link), and every accepted invite records a parent→child link in a queryable Drizzle table, with manager actions for force-adopt and forget.

**Architecture:** A per-guild list of opted-in role ids lives on the existing `guilds` table; one new `role_invite_tree` table stores one row per (guild, role, user) with a nullable `parent_user_id` (NULL = founding father / root). All five subcommands live under a new `invite` subcommand group on the existing `role` slash command in `src/modules/utilities/role.ts`; shared DB helpers and pure resolution logic live in a new underscore-prefixed helper module `src/modules/utilities/_inviteTree.ts` (skipped by the module loader). Invite messages are components-v2 containers with buttons routed through the module's existing `executeButtonCommand` via the standard `gm1:role:<action>:<arg>` customId scheme.

**Tech Stack:** Discord.js v14, TypeScript, Bun, Drizzle ORM / PostgreSQL.

**Spec:** `docs/superpowers/specs/2026-10-12-role-invite-trees-design.md` — read it; it owns all product decisions (permissions, founding fathers, no cascading, replacement of pending invites, forget semantics).

## Global Constraints

- `bun run check` (prettier `--write` + `tsc`) must pass at the end of **every** task. The repo has **no test suite** and the spec waives tests; pure-logic behavior is pinned by the case tables below instead.
- Prettier config (from `package.json`): tab width 4, single quotes, print width 150, `trailingComma: 'none'`, semis on.
- Imports use path aliases (`@classes/*`, `@builders/*`, `@src/*`) and **explicit `.js` extensions**.
- Validation-error replies are ephemeral: `flags: MessageFlags.Ephemeral` (match the existing style in `role.ts`).
- `client.db` is nullable. Before any DB access: `if (!client.db)` → reply `'Database not connected. Please try again later.'` ephemeral and return (pattern at `src/modules/factions/factions.ts:163-164`).
- Button customIds are `gm1:role:<action>:<arg>`; args must not contain `:` and the full id must be ≤ 100 chars (the builder throws otherwise).
- No new dependencies. Changes to `role.ts` are additive — do not modify the existing `give`, `create`, `delete`, `panel` flows.
- One conventional commit per task (`feat: ...`), matching existing history.

## Review Focus

These are the inputs the spec implies but no automated test exercises; each is pinned to the task that owns the code.

1. **Non-holder runs `/role invite invite`** → ephemeral error, nothing posted, no DB row. Pinned in Task 3, step 3 (validation order: resolution before any side effect).
2. **A user other than the target clicks Accept/Deny** → ephemeral "not your invite", no role change, row untouched. Pinned in Task 4, step 1 (`interaction.user.id !== row.user_id` check before any decision).
3. **Role deleted from Discord after the invite was posted** → clicking Accept yields an ephemeral "role no longer exists", the row stays `pending` (no crash, no orphaned decision). Pinned in Task 4, step 1 (role fetch before `markInviteDecided`).
4. **Target has DMs blocked** → the invite still succeeds via the channel message; only a warning is logged, the inviter gets their confirmation. Pinned in Task 3, step 3 (DM is `.catch`-swallowed after the message is posted).
5. **A role that was enabled is later deleted from Discord** → it stays in the enabled list but is inert: unselectable in role options, excluded from holder resolution (can't be in `roles.cache`), no crash in any subcommand. Pinned in Task 3, step 3 (holder set is computed as the intersection with `member.roles.cache`, never from the enabled list alone).

The three pure functions must match these case tables exactly (this is their spec — no test suite exists to pin them):

`resolveInviteRole(held, enabled, explicit?)` — inviter-side resolution:

| Case                                             | Result                                                                                         |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| `explicit` given, not in `enabled`               | `{ error: '<@&${explicitRoleId}> is not an invite-enabled role.' }`                            |
| `explicit` given, in `enabled` but not in `held` | `{ error: 'You do not hold that role.' }`                                                      |
| `explicit` given, in both                        | `{ roleId: explicit }`                                                                         |
| no `explicit`, `held ∩ enabled` empty            | `{ error: 'You do not hold any invite-enabled roles.' }`                                       |
| no `explicit`, intersection size 1               | `{ roleId: <the one> }`                                                                        |
| no `explicit`, intersection size > 1             | `{ error: 'You hold multiple invite-enabled roles. Specify which one with the role option.' }` |

`resolveManagerRole(enabled, explicit?)` — manager-side resolution (adopt/forget; the manager need not hold the role):

| Case                               | Result                                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------------------------ |
| `explicit` given, not in `enabled` | `{ error: '<@&${explicitRoleId}> is not an invite-enabled role.' }`                              |
| `explicit` given, in `enabled`     | `{ roleId: explicit }`                                                                           |
| no `explicit`, `enabled` empty     | `{ error: 'No invite-enabled roles in this guild. Enable one with /role invite enable first.' }` |
| no `explicit`, `enabled` size 1    | `{ roleId: <the one> }`                                                                          |
| no `explicit`, `enabled` size > 1  | `{ error: 'Multiple invite-enabled roles exist. Specify which one with the role option.' }`      |

`buildInviteJumpLink(guildId, channelId, messageId)` returns `` `https://discord.com/channels/${guildId}/${channelId}/${messageId}` ``.

The DB functions:

- `getEnabledTreeRoles`: `client.db.getGuild(guildId)` (nullable overload, no upsert); return `guild?.invite_tree_roles ?? []`.
- `setInviteTreeRoles`: `client.db.setGuild(guildId, { invite_tree_roles: roleIds })`.
- `getTreeRow` / `getTreeRowById` / `listPendingTreeRows`: plain selects with `eq` (and `and` for the triple); `listPendingTreeRows` filters `status = 'pending'`.
- `upsertTreeRow`: insert with `.onConflictDoUpdate({ target: [guild_id, role_id, user_id], set: { parent_user_id, status, channel_id, message_id, updated_at: new Date() } }).returning()` — conflict target is the unique triple, so an existing pending row is replaced in place. Return the single returned row.
- `markInviteDecided`: update `status` and `updated_at: new Date()` where `id`; no return.
- `setTreeMessage`: update `channel_id` and `message_id` where `id`; no return.
- `deleteTreeRow`: delete where the triple; return whether a row was removed (drizzle `delete...execute()` result or a pre-check select — implementer's choice).
- `invalidateInviteMessage(client, module, row)`: only when `row.channel_id && row.message_id`. Fetch the channel (`client.channels.fetch(row.channel_id)`) and message (`.messages.fetch(row.message_id)`) with `.catch(() => null)`; on missing, return silently (the message may have been deleted). Otherwise `message.edit(...)` with a components-v2 container rebuilt from the row: `TextDisplayBuilder` content `` `<@${row.parent_user_id ?? 'Unknown'}> invited <@${row.user_id}> to <@&${row.role_id}>` `` plus an `ActionRowBuilder` holding both buttons **disabled** — `new GargoyleButtonBuilder(module, 'inviteaccept', String(row.id)).setLabel('Accept').setStyle(ButtonStyle.Success).setDisabled(true)` and the `invitedeny`/Deny/Danger equivalent. `flags: [MessageFlags.IsComponentsV2]`. Catch edit errors and log via `client.logger.warning` — a failed invalidation must never break the calling flow.

### Task 7: `/role invite tree` (tree view)

Added after user request (2026-10-13): "a tree view so that you can see who invited whom, potentially render it as an image or as an ASCII tree."

Design (controller's calls, user approved the feature request in chat):

- **ASCII tree in a code block** (reliable, copy-pasteable, no rendering failure modes). Image rendering via the existing `canvas` dependency is a possible follow-up, not built now.
- Command: `/role invite tree [role]` — added to the existing `invite` group. `role` is optional with the manager-style resolution (`resolveManagerRole`): required when multiple roles are enabled.
- **No `ManageRoles` gate**: any guild member may view it. The tree only shows guild members' names (public info in a guild) and who invited whom.
- The tree contains **`accepted` rows only** — pending and denied offers are not part of the tree.
- **Orphan guard**: a row whose `parent_user_id` has no row of its own (e.g. the parent was forgotten) is rendered as a root. Links are permanent history; the view must not drop or crash on orphans.
- Output cap: if the rendered tree exceeds ~1800 characters, truncate at a node boundary and append a `… (N more members not shown)` line, so the whole reply stays under Discord's 2000-char message limit.

**Files:**

- Modify: `src/modules/utilities/_inviteTree.ts` (two new exports)
- Modify: `src/modules/utilities/role.ts` (subcommand + dispatch branch)

**Interfaces:**

- Consumes (Tasks 1–2): `getEnabledTreeRoles`, `resolveManagerRole`.
- Produces:
    - `getAcceptedTreeRows(client: GargoyleClient, guildId: string, roleId: string): Promise<InviteTreeRow[]>` — select where the (guild, role) triple matches and `status = 'accepted'`.
    - `renderInviteTree(rows: Array<{ user_id: string; parent_user_id: string | null }>, names: Record<string, string>): string` — pure function, the tree renderer (spec below).

- [ ] **Step 2: Add the pure `renderInviteTree` to `src/modules/utilities/_inviteTree.ts`**

Behavior (this is its spec — no test suite exists to pin it):

- Build a children map: `parent_user_id → rows[]`. A row is a **root** when its `parent_user_id` is null **or** when no row in the set has `user_id === parent_user_id` (orphan guard). Children are ordered by `created_at` ascending (the rows passed in are DB-order; accept either `created_at` sort or input order — pick one, document in a comment).
- Render classic box-drawing indentation:

```text
Alice
├── Bob
│   └── Carol
└── Dave
```

i.e. each child line is prefixed with `├── ` (more siblings follow) or `└── ` (last sibling), and each ancestor level contributes a `│   ` or 4-space prefix. Use `names[user_id]` for display; if a name is missing from the map, use `@${user_id}`.

- Truncation: if the full rendering would exceed 1800 characters, stop at the last node boundary that fits and append one final line `… (N more members not shown)` where N is the number of rows not rendered.
